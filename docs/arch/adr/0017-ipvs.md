# Add IPVS (LVS) load-balancer collector via direct generic-netlink, runtime-gated

## Context and Problem Statement

IPVS (IP Virtual Server / Linux Virtual Server) is the kernel's layer-4
load-balancing subsystem, exposed as a generic-netlink family named "IPVS" with
version 1. It tracks per-virtual-service and per-real-server connection,
packet, and byte counters that are essential for observing LVS-based
load-balancer health.

Three distinct approaches exist for reaching these counters from userspace:

1. The procfs paths `/proc/net/ip_vs` and `/proc/net/ip_vs_stats` are available
   when the `ip_vs` kernel module is loaded. They expose aggregate per-service
   and per-destination text tables, but the format is undocumented at the UAPI
   level and the stats64 variant (IPVS_STATS_ATTR_CONNS64 and friends) is
   absent from the procfs representation.

2. The `ipvsadm` CLI (`--list --stats`) uses the same generic-netlink family
   under the hood; its output is not machine-readable in a stable structured
   form.

3. Direct generic-netlink via `NETLINK_GENERIC` (family 16) using the same
   `CTRL_CMD_GETFAMILY` resolution path already in use for the ethtool
   collector. Commands `IPVS_CMD_GET_INFO`, `IPVS_CMD_GET_SERVICE`, and
   `IPVS_CMD_GET_DEST` return structured `nlattr` trees with
   `IPVS_SVC_ATTR_*`, `IPVS_DEST_ATTR_*`, and `IPVS_STATS_ATTR_*` /
   `IPVS_STATS64_ATTR_*` attributes defined in
   `include/uapi/linux/ip_vs.h`.

On hosts where `ip_vs` is not loaded, `CTRL_CMD_GETFAMILY` for "IPVS" returns
`ENOENT`. This is an expected runtime condition (not an error) on hosts that do
not run an LVS load-balancer. The collector must be runtime-gated: report
`nft_scrape_collector_available{collector="ipvs"}=0` and suppress all
`nft_ipvs_*` series without incrementing error counters.

The probe host does not have `ip_vs` loaded (kernel module absent). This ADR
records the design decision in the presence of that grounding constraint and
defines the full runtime-gating contract so that integration tests can verify
both the present and absent code paths.

## Considered Options

- **Skip**: do not implement the IPVS collector. LVS operators would need a
  separate exporter (e.g. `kube-proxy` metrics or `prometheus/node_exporter`
  with the `ipvs` collector). This leaves a gap for bare-metal LVS deployments
  that use `nft_exporter` as their single node metrics source.

- **Procfs-based collection** (`/proc/net/ip_vs` and `/proc/net/ip_vs_stats`):
  avoids the generic-netlink surface. Drawbacks: the text format is
  undocumented and has changed across kernel versions; stats64 values are absent
  (truncating counters on busy services within hours); the procfs path is not
  guaranteed to exist even when `ip_vs` is loaded with non-default kernel
  configurations (`CONFIG_IP_VS_DEBUG` required for the debug proc entry).

- **Direct generic-netlink** (chosen): `IPVS_CMD_GET_INFO` provides the
  current table size (active connections + connection table total). Dump-mode
  `IPVS_CMD_GET_SERVICE` iterates all virtual services. Per-service
  `IPVS_CMD_GET_DEST` enumerates real servers. The `IPVS_SVC_ATTR_STATS64` and
  `IPVS_DEST_ATTR_STATS64` nested attributes provide 64-bit counters
  (`IPVS_STATS64_ATTR_CONNS`, `_INPKTS`, `_OUTPKTS`, `_INBYTES`,
  `_OUTBYTES`) plus rate sub-attributes (`_CPS`, `_INPPS`, `_OUTPPS`,
  `_INBPS`, `_OUTBPS`). This path is consistent with ADR-0011 (direct wire
  protocol) and reuses the `NETLINK_GENERIC` socket already held by
  `EthtoolAdapter`. Cardinality is bounded by operator-controlled config
  (service and destination counts are fixed by the operator's LVS
  configuration, not by runtime traffic).

## Decision Outcome

**Chosen option: direct generic-netlink over NETLINK_GENERIC, runtime-gated.**

### Bounded context

A new bounded context `ipvs` is introduced. Its driving port is
`NetlinkIpvsPort`. The collector strategy is `IpvsCollector`. The adapter crate
is `nft_exporter_adapter_ipvs`.

### Collection sequence

```
Phase 1 — Family resolution (once per process, OnceLock<u16>):
  CTRL_CMD_GETFAMILY("IPVS\0") -> family_id | ENOENT -> runtime-gated

Phase 2 — Info query (one unicast request):
  IPVS_CMD_GET_INFO -> active_connections + conn_tab_size

Phase 3 — Service dump (NLM_F_DUMP):
  IPVS_CMD_GET_SERVICE -> one reply per virtual service
  Each reply carries IPVS_SVC_ATTR_AF, _PROTOCOL, _ADDR, _PORT or _FWMARK,
  and nested IPVS_SVC_ATTR_STATS64.

Phase 4 — Destination dump per service:
  IPVS_CMD_GET_DEST (unicast, one request per service) ->
  one reply per real server; each carries IPVS_DEST_ATTR_ADDR, _PORT,
  and nested IPVS_DEST_ATTR_STATS64.
```

### Runtime gating

When `CTRL_CMD_GETFAMILY("IPVS\0")` returns `ENOENT`:

- Emit `nft_scrape_collector_available{collector="ipvs"}` with value `0`.
- Emit no `nft_ipvs_*` series.
- Do not increment `nft_scrape_collector_error_total`.
- Set `nft_scrape_collector_success{collector="ipvs"}` to `1` (the collector
  ran successfully; it correctly detected that the subsystem is absent).

This mirrors the ethtool family-resolution gating established in ADR-0011
section 8.1.

### Cardinality bounds

Service labels: `{proto, vip, port}` where `vip` is an anonymised VIP string
(IPv4 or IPv6 presentation form) and `port` is a decimal port number string;
or `{proto="fwmark", vip="", port="<fwmark_hex>"}` for firewall-mark services.
A fourth label variant uses `port=""` when `vip` is a `0.0.0.0` wildcard.

Destination labels: `{proto, vip, port, rip, rport}` where `rip` is the real
server address and `rport` is its port. Cardinality is bounded by the number of
(service, destination) pairs, which is operator-controlled configuration data.

The config key `ipvs_max_services` (default 512) and `ipvs_max_dests_per_service`
(default 256) act as cardinality guards. Exceeding either ceiling aborts the
dump and increments
`nft_scrape_collector_error_total{collector="ipvs", reason="cardinality_overflow"}`.

### STATS64 precedence

`IPVS_SVC_ATTR_STATS64` and `IPVS_DEST_ATTR_STATS64` nested attributes are
preferred when present (kernel >= 3.15). Fall back to the 32-bit
`IPVS_SVC_ATTR_STATS` / `IPVS_DEST_ATTR_STATS` only when the 64-bit variants
are absent (kernel < 3.15; treated as a legacy code path). Rate sub-attributes
(`_CPS`, `_INPPS`, `_OUTPPS`, `_INBPS`, `_OUTBPS`) are emitted as gauges; the
kernel computes these as exponential moving averages over 1-second windows.

### Consequences

- Positive: LVS operators gain per-service and per-destination connection,
  packet, and byte counters with no external exporter dependency.
- Positive: Runtime gating means `ip_vs` absence does not increment error
  counters or affect `nft_up`; non-LVS hosts are unaffected.
- Positive: Consistent with ADR-0011 direct-wire mandate; no procfs parsing,
  no undocumented text format, no `ipvsadm` subprocess.
- Positive: STATS64 path avoids 32-bit counter overflow on busy services
  (millions of connections per second saturate a u32 within minutes).
- Negative: Phase 4 (per-service destination dump) issues one unicast request
  per service. On a host with many virtual services this produces N+1 round
  trips. The cardinality guard (`ipvs_max_services`) limits worst-case round
  trips. A future optimisation could use `IPVS_CMD_GET_DEST` with
  `NLM_F_DUMP` and filter by service key once kernel support is confirmed.
- Negative: IPv6 VIP and real-server addresses are 16 bytes; their presentation
  form as labels increases per-series byte cost compared to IPv4. The cardinality
  guard mitigates this.
